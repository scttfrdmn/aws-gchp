3. THE OFFLINE INSTRUMENT ALREADY EXISTS: LITH_PF_TRACE
-------------------------------------------------------
Upstream's stated next step is offline: find what predicts prefetch follow-through from
a recorded read trace, rather than buying a GCHP run per hypothesis (four hypotheses so
far, ~35 min of a c8g.48xlarge each). `LITH_PF_TRACE=<path>` does most of that already
and is present in v1.1.3, main and the PR (internal/fuse/fs.go:283, tracePF :294,
called :785). One CSV row per read:

  key,off,len,blk,gap,state_before,state_after,peak_window

Probe on a real 106 MiB HEMCO object (AEIC/v2015-01/AEIC.nc), three single-handle
patterns driven by os.pread on one fd (so each pattern is ONE handle, unlike dd):

  pattern                          rows  transitions recorded                deestab
  contiguous 24 MiB                 193  cold->sequential                      0
  40 x 1 MiB at 2.5 MiB stride      270  cold->seq, seq->cold, cold->seq       1
  6 x (6 MiB run + 37 MiB jump)     113  cold->random, random->sequential      1

So the detector's decisions are observable and the counter agrees with the trace.
(Probe caveat, stated because it limits what the numbers mean: after the first phase the
106 MiB object was cache-resident -- issued stayed at 91 while used grew 9 -> 69 -> 74 --
so this demonstrates the INSTRUMENT, it does not measure HEMCO's real pattern.)

Three gaps, filed as lith#262:
  (1) NO HANDLE DISCRIMINATOR. Rows carry `key`, not a handle. Three sequential handles
      on one object gave 576 rows under one key with nothing to separate them; under the
      real workload 48 ranks funnel through one daemon and ExtData re-opens the same
      files every timestep, so it is dozens interleaved. Since the prefetcher is per
      `Open` (fs.go:562), the trace cannot be grouped by the thing that decides. An `fh`
      column fixes it; `pid` would also let a multi-rank trace split by rank.
  (2) READS SILENTLY OMITTED. fs.go:772 skips the prefetcher -- and therefore the trace
      -- while a whole-file parts fetch is in flight, and for footer-family handles.
      Defensible for the prefetcher, but it makes the trace a BIASED SAMPLE with no
      marker: on HEMCO, `parts-max auto` resolves to 64 MiB at --nic-gbps 50 and 202 of
      471 manifest objects are >32 MiB, so the omitted reads are a large non-random
      share of the bytes.
  (3) NO DISPATCH/WINDOW RECORD. Follow-through must be re-derived by replaying rows
      through prefetch.Prefetcher and scoring dispatched blocks against each handle's
      FUTURE reads. Replay is the right design (policy-independent trace, evaluate any
      candidate offline) but it needs the mount config in force (a header line) to
      construct the same prefetcher, and a `window`/dispatch-count column to validate
      the replay's fidelity before trusting its verdict on a new policy.
  Minor: undocumented outside a struct comment; os.Create silently truncates and
  silently no-ops on error (a typo'd path = an empty trace and a successful-looking
  run); unbounded and serialized under one mutex, so leaving it on in production adds a
  global lock to every read.

WHAT THIS BUYS
--------------
With (1) and (2), the real 48-rank C24 fullchem trace can be captured at ZERO marginal
cost on an already-scheduled job, for the pathological mount (HEMCO, 16.5% hit, 2.405x)
and the healthy control (met, 79.7%, 1.210x) in the SAME process -- which is the
comparison the follow-through question needs. Then hypothesis 5 costs a replay instead
of a cluster run, and if nothing in recorded reads separates met's handles from HEMCO's,
that is the documented-limitation answer reached for free.
