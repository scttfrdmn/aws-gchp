WHY THIS GATE EXISTS
--------------------
Gate 5b: HEMCO's 2.44x amplification is a PRECISION defect, not a size one (4x smaller
window -> linearly less bad prefetch, same hit rate). Gate 5c: upstream's first fix
(#259, evidence-ratio) cut prefetch volume 45% but cut USED 53%, so the hit rate went
DOWN -- a volume cap, not a precision fix, and upstream merged it described as such.

PR #260 is hypothesis 4, and upstream's premise for it was explicit: HEMCO's handles
"oscillate" -- they establish, lose establishment, re-establish, over and over, and each
re-establishment commits another window that the subsequent reads do not use. The cited
evidence was `lith_prefetch_reset_random_total` = 307-332 per run on the HEMCO mount:
"the detector notices every time and then forgets, ~320 times per run." `--readahead-
reestablish-max N` stops re-establishing after a handle has lost establishment N times:
contiguous progress is still recognized, reads are still served, but nothing further is
committed.

Upstream asked for N=2 on HEMCO, optionally N=4, and pre-registered both the predictions
and the kill condition (below).

WHY: `reset_random` IS NOT `deEstablished`, AND THE PREMISE RESTED ON THE WRONG ONE
----------------------------------------------------------------------------------
From internal/prefetch/prefetch.go in the PR's own tree:

  func (p *Prefetcher) deEstablish() {
      if p.established {          // :235-240
          p.deEstablished++
      }
      p.established = false
  }

versus the two `resetRandom++` sites:

  if p.covMin > 0 && cov < p.covMin {   // :505-512, coverage gate
      if p.state != Random { p.resetRandom++ }
      ...
      p.deEstablish()
  }
  // second unexplained jump                // :522-532
  p.state = Random; p.deEstablish(); ...; p.resetRandom++

`resetRandom` counts collapses to the Random STATE. `deEstablished` counts only losses of
an ESTABLISHMENT that existed. On HEMCO those differ by 20-30x: ~320 state collapses,
10-17 establishment losses. The premise -- "the detector notices ~320 times per run and
then forgets" -- read the first number as if it were the second. The oscillation #260
gates happens about 3-5% as often as the signal cited for it, which is why a cap at N=2
or N=4 never triggers (zero suppressions) and amplification lands on top of three
independent defaults measurements.

THE FINDING (and it is a positive one): THE DEFECT IS AT COMMITMENT, NOT RE-COMMITMENT
--------------------------------------------------------------------------------------
Put the two new counters next to the volume they have to explain. HEMCO issues ~4500-4800
1 MiB prefetch chunks per run and loses establishment 10-17 times. Prefetch is only
committed from an established handle, so those thousands of committed chunks are NOT the
product of repeated re-establishment. They come from handles that establish ONCE -- pass
the #229 coverage test legitimately -- and then keep growing and committing windows that
their subsequent reads never use, all the way to close, without ever tripping a
de-establishment at all.

That relocates the defect precisely, and it is consistent with every earlier arm:
  - #259 bounds the window at establishment AND growth: it moved volume 45%.
  - #260 gates RE-establishment: it moved nothing, because re-establishment is rare here.
  - 5b: window SIZE is irrelevant to the hit rate; 5c: within-handle accrued evidence is
    uncorrelated (slightly anti-correlated) with whether a prefetch gets used.
So the live target is the decision an ALREADY-ESTABLISHED handle makes to commit the next
window, and the discriminator cannot come from that handle's own history -- 5c measured
that history and it does not carry the signal. It has to come from state that outlives the
handle (per-mount / per-directory-family), which is what gate 5b concluded and what #260
was explicitly designed to avoid needing.

AND THE INVERSION: OSCILLATION IS A MARKER OF THE HEALTHY MOUNT, NOT THE SICK ONE
---------------------------------------------------------------------------------
                      reset_random   deestablished   share   hit rate   ampl
  HEMCO (2.4x, sick)      321             10          3%      16.5%    2.405x
  MET   (1.21x, healthy)  113             51         45%      79.7%    1.210x

Met loses establishment 3-5x MORE often than HEMCO, in absolute count and as a fraction of
its Random collapses -- and met is the mount whose prefetch works. Met's handles sweep a
met field, re-anchor, and sweep again; that re-anchoring is exactly the behaviour #260
suppresses, and it is productive. So de-establishment frequency does not separate the good
reader from the bad one here; it points the wrong way. Arm J is the direct measurement:
the cap fired 16 times on met and met's amplification and hit rate did not budge (1.210x,
79.7%, used/issued 2347/2943 vs the control's 2351/2948) -- so the multi-pass regression
upstream worried about did not materialize at N=2 on this workload, but only because met's
prefetch is already so accurate that 16 refused windows are lost in the noise. On a
sweep-heavy mount with a lower baseline the same 16 refusals would be a real cost, and
nothing in this gate says they wouldn't be.

COUNTER PAPERCUT (reported on #260)
-----------------------------------
`PrefetchReEstablish` only adds to the registry when the value is > 0, so a zero-valued
labelled counter emits NO SERIES AT ALL. "Zero suppressions" therefore has to be inferred
from the absence of a line, which is indistinguishable in a scrape from "the binary does
not have the feature", "the label value differs", and "the mount was never opened". In
this gate that ambiguity was resolvable only because arm J proved the same binary DOES emit
the series when it fires. Emit labelled counters at zero once a mount has served a read.
