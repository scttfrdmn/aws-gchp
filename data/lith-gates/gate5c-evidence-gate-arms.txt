WHY THIS GATE EXISTS
--------------------
Gate 5b's five arms (A-E) established that HEMCO's 2.44x read amplification is not a
size problem. Cutting the readahead window 4x (C 32 MiB -> D 8 MiB) cut the VOLUME of
bad prefetch almost linearly (4086 -> 2044 MB) and left the HIT RATE where it was
(16.1% at A, 13.0-13.8% at C/D/E) against met's 80% on the same box in the same job.
Window tuning bottomed out at 1.895x with ~2.0 GB of decision-scaled waste surviving the
MINIMUM 1-block window with all three whole-file paths disabled.

Upstream's diagnosis of the residue: lith builds one prefetcher per Open
(internal/fuse/fs.go:562, `pf: newPFWrapper(...)` inside the handle literal), so it dies
at close and every one of ~2400-4600 decisions in a run is made cold, with no memory of
the thousands before it. PR #259 is their proposed fix that does NOT require cross-handle
state: `--readahead-evidence-ratio k` bounds a committed window to k x the bytes the
handle has actually read, applied at establishment, at window growth, and at
re-establishment. Off by default.

THE FINDING: #259 IS A BETTER-ENGINEERED VOLUME CAP, NOT A PRECISION FIX
------------------------------------------------------------------------
By upstream's own stated decision criterion the answer is no. The gate cut prefetch
ISSUED by 45% (4631 -> 2567) and cut USED by 53% (775 -> 366). Because used fell FASTER
than issued, the hit rate fell rather than rose. The accrued-evidence signal is not
correlated with whether a prefetch will be used -- if anything it is very slightly
anti-correlated, because the handles with the most evidence are the ones reading the
large HEMCO files whose scattered hyperslabs are exactly what the prefetcher cannot
predict.

k orders correctly, so the knob does what it says: tighter k -> less prefetch.
  k=8   2567 issued   1.956x
  k=32  3633 issued   2.206x
  off   4631 issued   2.425x

And it lands where the static minimum window landed:
  D (--max-readahead 1, a hard 8 MiB pin)   7122.3 MB   1.925x
  F (--readahead-evidence-ratio 8)          7231.8 MB   1.956x
Same floor, 1.5% apart. That is the useful part of the result for upstream: #259 reaches
the static minimum window's saving WITHOUT pinning readahead for well-behaved readers --
a sequential copy still earns the full window once it has consumed
max-readahead*block-size/k. As an ergonomics and safety improvement over telling users to
set --max-readahead 1 globally, it is real. As the answer to #256's precision question,
it is not, and the two should not be conflated when the PR merges.

The residual is 1219.6 - 1265.9 MB across EIGHT fetch policies spanning 1.895x to
2.438x, and 1225.4 - 1228.8 MB across the three arms here -- a 0.3% span. Gate 5b
established that constancy across window and whole-file knobs; gate 5c extends it to a
mechanism of an entirely different kind. This is the strongest number in either gate:
~1.23 GB of HEMCO's traffic is demand reads paying whole 1 MiB chunks for sub-MiB
hyperslabs, and no fetch policy touches it.

Corroborating constants, unchanged by the gate:
  lith_read_straddle_total      A 3055   F0 3066   F 3062   G 3033
  lith_prefetch_reset_random    A  332   F0  316   F  307   G  321
  lith_prefetch_window_halved      0 in all eight arms (prefetch.go:404 needs an
                                   intra-handle SEEK; open-read-close never gives one)
  lith_prefetch_evicted_unread     0 (no cache pressure: 32 GB cache, 9.1 GB fetched)
  lith_fill_runs_total             0 (GCHP never establishes a sequential fill run)

The straddle count is the demand floor's fingerprint: ~3060 straddling reads, constant
to 1% across every policy, is the same population as the ~1.23 GB residual. Those reads
are gated OUT of lith's byte-exact demand path by internal/fuse/fs.go:740
(`if sequential && h.pf.state() == prefetch.Random`), so a spuriously-established handle
is DENIED byte-exact reads and pays a whole chunk. That is why the floor should move when
the classifier stops mis-establishing -- and why the real target is ~1.0x, not ~1.9x.

GETs rise as the gate tightens (smaller fetches, same bytes wanted):
  F0 8166   G 8827   F 9237   (gate 5b: A 8183 ... E 9259)
In-region GET cost is ~$0.004/run at this rate and in-region bytes are free, so this is
a cost/egress finding with no performance consequence: sim-only wall is 186-187 s in all
EIGHT arms, and init spans 178.8-189.5 s with no ordering by GET count.

WHAT IS STILL UNRESOLVED AFTER 5c
---------------------------------
Nothing in the observable metrics distinguishes a window the gate refused from a window
it never wanted, because the PR adds no counter for a denied or clamped commitment --
the only evidence of the gate acting is that `issued` fell. If #259 lands, a
`prefetch_evidence_clamped_total` (and ideally the bytes clamped) would make the next
person's job a scrape instead of an inference.

The precision defect itself is untouched and still needs what gate 5b concluded it
needs: state that outlives a handle (per-mount or per-directory-family), plus revisiting
the fs.go:740 gate so a misclassified handle is not additionally punished by losing
byte-exact reads.

HARNESS TRAP THIS GATE ADDED, AND IT COST A SUBMISSION
------------------------------------------------------
`sbatch --export=ALL,ARMLIST=F0,F,G` DOES NOT WORK: sbatch splits --export on COMMAS, so
ARMLIST was set to "F0" and sbatch then tried to export two variables named F and G.
Job 18 ran arm F0 alone, printed a clean and correct verdict for it, and silently
dropped the two arms the job existed to run. Nothing in the log was wrong; the
submission was. Correct form is `ARMLIST=F,G sbatch --export=ALL <script>`. Recorded in
the harness header so the next person does not re-buy it.
