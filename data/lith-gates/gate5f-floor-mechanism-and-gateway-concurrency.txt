PART B (#256) — THE FLOOR IS A PER-HANDLE COLD-START TAX
-------------------------------------------------------
Correction to my own earlier pointer: the straddle branch is NOT the floor.
BlockStore.GetRange is extent-aware per chunk (#118), so a straddling sub-MiB read is
byte-exact, and HEMCO's constant 3074 straddles are innocent.

The floor is the in-chunk branch, fs.go:778-786:

    sequential := h.footerKind == footer.FormatNone || h.footerStream   // TRUE, plain handle
    if sequential && h.pf.state() == prefetch.Random {
        if t := f.byteExactThreshold(); t > 0 && end-off <= t { sequential = false }
    }
    chunk, err := f.store.Chunk(..., sequential)

and in Chunk(): `if sequential { want = maskForLen(chunkLenOf(ci, objSize)) }` — the
whole 1 MiB chunk. Byte-exactness is granted ONLY in Random. A `cold` handle — not yet
classified at all — is fetched as if it were streaming.

Probe: 128 x 64 KiB reads, each 7 MiB past the last, 64 KiB-aligned,
--prefetch-budget 1MB so readahead cannot confound.

  trace (gate5f-b2-align-trace.csv):
    rows 1-16   cold -> cold      gap = 7 274 496 on every read
    row  17     cold -> random
    rows 18-128 random -> random

  lith_fill_bytes_total{kind="demand"} = 24 051 712 = 367 x 64 KiB over 112 fills,
  which factors UNIQUELY as 17 x 16 extents + 95 x 1 extent (16a + (112-a) = 367 => a=17)
  — and 17 is exactly the count of reads the trace shows in `cold`.

  => the first 17 reads each paid 1 MiB for 64 KiB, while the detector was looking at a
     7.27 MB gap on every one of them.
  => waste 17 x (1 MiB - 64 KiB) = 15.94 MiB on ONE handle, against 1.06 MiB requested
     in that phase; net of 16 later cache hits on those chunks, ~15 MiB.

Invariance (same 128 reads, five arms):

  arm  alignment    flags                              distinct     s3_bytes  GETs  straddles
  b1   misaligned   defaults                         16 777 216   30 277 632   112        15
  b2   64 KiB-align defaults                          8 454 144   24 051 712   112         0
  b3   64 KiB-align --coalesce-gap 1B                  8 454 144   24 051 712   112         0

Byte-identical across the coalesce gap and across a 50x change in claimed NIC bandwidth.
Misalignment doubles the extents a read touches (numerator AND denominator) and leaves
the cold-phase tax unchanged. Nothing a fetch-policy flag reaches — which is the
signature of a floor that held at 1219.6-1265.9 MB across TWELVE policies spanning
1.895-2.461x: the granularity commitment is not bounded by evidence, window, or ratio,
it is decided by a state the handle has not reached yet.

Arithmetic bridge, pre-registered as falsifiable:
  1224.3 MB / (1 MiB - 64 KiB) = 1245 pre-decision small reads across all HEMCO handles
  in the 48-rank run; at <=17 per handle that needs >=73 handles, and a 471-object
  working set re-opened per timestep under 48 ranks clears that easily.
  FROM THE REAL TRACE (free, now that rows carry fh and path): group by fh, count rows
  with path=window, len <= byteExactThreshold, state_before=cold, multiply by
  (chunk length - extents the read covers). PREDICTION 1.0-1.4 GB. Below 0.5 GB and the
  mechanism is wrong.

Same defect as gate 5d's, one level over: both waste channels are commitments made on no
evidence. #259 bounded the window at establishment and growth (-45% volume). The
granularity commitment has no bound at all: "sequential until proven random" where the
honest posture is "unknown until proven sequential".

Candidate fix and its real cost: treat cold like Random for the granularity decision when
the read is <= byteExactThreshold AND the gap is large (gap exists from read 2). Cost
lands on a streaming reader that starts small — extra GETs before classification, i.e.
latency and request count against bytes. The mount paying the tax is the one that never
streams: 33% of HEMCO's distinct bytes vs 1.8% of met's.

PART C (#256) — used/issued IS A CHUNK-TOUCH RATE, NOT A BYTE RATE
------------------------------------------------------------------
Same object, same scattered pattern, readahead left on:

  lith_prefetch_issued_total            91
  lith_prefetch_used_total              81    -> 89.0% "hit rate"
  lith_fill_bytes_total{kind="whole"}   95 033 055
  lith_fill_bytes_total{kind="demand"}  12 320 768
  lith_distinct_bytes_read              23 855 104
  (fills sum exactly to lith_s3_bytes_total 107 353 823)

Granting EVERY distinct byte to the readahead path, its bytes were read to at most
23.86/95.03 = 25.1%; netting out what the demand fills must have served, ~12%. Against
89% reported. A 1 MiB chunk counts as "used" when a 64 KiB read touches it.

Consequences:
  1. On met, chunk-touch and byte follow-through nearly coincide (a sweep reads chunks
     whole). On HEMCO they cannot. So the 79.7% vs 16.5% gap quoted all campaign
     UNDERSTATES the real difference, and every arm scored "hit rate didn't move" was
     scored on the friendlier number.
  2. It fixes the unit for the replay scorer.

Asks: lith_prefetch_used_bytes_total, or (better for the offline route) a per-read trace
column s3_added = bytes this read caused to be fetched. Either makes the floor decompose
EXACTLY offline instead of by bounds.

SCORING RULE, PRE-REGISTERED (upstream writes the scorer, we capture)
--------------------------------------------------------------------
  - score BYTES, not chunk touches: for each dispatched block, the fraction of its bytes
    the same handle (fh) reads before close; per-handle distributions, met vs HEMCO.
  - SEPARATION EXISTS iff a feature from a handle's first k<=8 reads (gap distribution,
    read sizes, offset monotonicity, straddle fraction) predicts per-handle byte
    follow-through with Spearman |rho| >= 0.5, fit on one arm's handles, tested on
    another's.
  - NO SEPARATION iff best |rho| < 0.5 AND met-vs-HEMCO per-handle distributions overlap
    at rank-sum AUC < 0.7 — the documented-limitation answer, reached for free.
  Agreed in writing before either side has data, so it cannot be tuned to the result.
