Ground truth available for free: gate 5f's b2 arm, where the cold-start tax was derived

PART A (#265) — THE DOCUMENTED SPELLING NOW WORKS, THREE WAYS
------------------------------------------------------------
Same object, same 128 x 64 KiB scattered reads, --prefetch-budget 1MB, main f75d737:

  arm          how tracing was requested            trace file      rows
  a1-flag      --pf-trace <path>                    created         128
  a2-env       LITH_PF_TRACE=<path>  (the control)   created         128
  a3-both      both set                             FLAG file only   128
  a4-badpath   --pf-trace /nonexistent-dir/x.csv    none (by design)  -

  a1 vs a2, diffed ignoring the pid column: IDENTICAL.
  a3: the env-var path was NOT created — flag wins at fs.go:288, no double-write.
  a4: level=ERROR msg="prefetch trace disabled: cannot create file" — and this is the
      part that could not happen before #265: with PFTracePath always "", #263's
      loud-on-create-failure was unreachable. Wiring the flag restored its own safety net.
  Bytes unperturbed by tracing: s3_bytes = 24 051 712 in all three traced arms, the same
      figure gate 5f's b2 arm measured untraced.

ONE ASK FROM a4: the mount CONTINUES after the ERROR. For a local experiment that is
right. For a capture that costs a 35-minute 48-rank job, a typo'd path now means the run
completes, costs full price, and produces nothing — the failure is loud in a log nobody
reads until afterwards. Want `--pf-trace` create failure to be FATAL at mount time (or a
`--pf-trace-required`), so the capture fails in the first second instead of the 35th minute.

PART B (#267 vs gate 5f) — THE COLD-TAX COUNTER REPRODUCES 17, AND CORRECTS MY MiB
---------------------------------------------------------------------------------
Prediction posted in #256 before running this: cold_small_reads = 17, waste = 16 711 680.

  trace                     cold_small_reads   waste bytes     fidelity
  gate5g a1-flag                    17          16 646 144     OK
  gate5f b2-align (banked)          17          16 646 144     OK

Count: EXACT match, from the replay of recorded reads rather than from the metric
factorization. Two independent derivations of the same 17.

Waste: mine was 65 536 B (one 64 KiB extent) high. Cause found in the trace: the first
read of the handle is 131 072 B, not 65 536 — the kernel merged it — so the true figure is
16 x (1 MiB - 64 KiB) + 1 x (1 MiB - 128 KiB) = 16 646 144 = 15.875 MiB, not 15.94 MiB.
#267's number is the correct one; gate 5f's MiB figure is 0.4% high and the count stands.
(A pure-64 KiB handle does give exactly 16 711 680 — see the scatter handles in Part C.)

Adversarial: header stripped -> the scorer REFUSES with the right reason ("predates the
replayable format (#262) and cannot be replayed faithfully") instead of guessing a block
size. Good.

PART C (#267 end-to-end on real traces) — FOUR DEFECTS, ONE OF THEM VOIDS THE VERDICT
------------------------------------------------------------------------------------
Two labelled arms x two replicates, 12 handles each, prefetch ENABLED, same object:
  stream  (met surrogate)   192 x 128 KiB contiguous over a 24 MiB span, per handle
  scatter (HEMCO surrogate) 48 x 64 KiB reads 7 MiB apart, per handle

C1. FIDELITY REPORTS "OK" WHILE THE DISPATCH TOTAL IS 12x THE MOUNT'S OWN COUNTER.
    The scorer's own output for c1-stream:
      5 prefetching handles, dispatched_bytes = 1 887 436 800 + 4 x 1 870 659 584
                                              = 9 370 075 136 B  (1117 blocks of 8 MiB)
      byte follow-through: median 0.000, mean 0.001
    The same run's mount counters:
      lith_prefetch_issued_total = 91          (blocks)
      lith_s3_bytes_total        = 111 810 271 (the whole object, exactly once)
    1117 vs 91 = 12.3x.  9.37 GB vs 111.8 MB = 83.8x. The object is 13.33 blocks long, so
    no handle can have more than ~14 useful blocks; 223 = max_readahead is dispatched
    wholesale and 94% of the denominator lies past EOF.

    Why fidelity misses it: the check compares `len(p.Observe(...))` against the trace's
    `dispatched` column — and BOTH come from Observe. It validates the trace against
    itself. What the mount actually issued (after EOF clamp, budget and in-flight dedup)
    is a different number, and it is already exported.

    Consequence for the capture: byte follow-through would have come out ~0 for every
    handle on both mounts, which reads as "prefetch never pays off" and is an artifact.
    Sanity bound from the counters instead: distinct 59 899 904 / whole-kind fills
    95 033 055 <= 63%, against the scorer's 0.45% — two orders of magnitude.

    Fix shape: clamp dispatched bytes to the object size (needs a size column or header
    field — the trace does not carry one), and make fidelity compare the replayed total
    against `lith_prefetch_issued_total` from the same run.

C2. AUC IS COMPUTED ON labels[0] vs labels[1] ONLY, SILENTLY.
    The rule requires fit-on-one-arm / test-on-another, i.e. >= 4 traces (2 mounts x 2
    arms). Ordered the natural way — hemcoA hemcoB metA metB — the AUC half then compares
    HEMCO against HEMCO. Demonstrated:
      lith-pfreplay sA=stream sB=stream xA=scatter xB=scatter
      -> "AUC(sA vs sB) on byte follow-through = 0.500 (n=5 vs 5)"
    0.500 is exactly right for one population sampled twice, and it is being fed to a rule
    that reads AUC < 0.7 as evidence of NO SEPARATION. Arm order silently decides it.

C3. AUC VANISHES WHENEVER ONE ARM DISPATCHES NO PREFETCH — AND THAT IS THE HEMCO CASE.
    The scatter arm's handles all have follow-through NaN (0 blocks dispatched: large gaps
    keep the detector in Random). byLabel[scatter] is empty, aucMannWhitney returns not-ok,
    and NO AUC LINE IS PRINTED AT ALL. The verdict then falls through to the Spearman
    branch. HEMCO on the real mount has prefetch_issued near zero by the same mechanism, so
    the no-separation branch of the pre-registered rule may be UNREACHABLE on exactly the
    data it was written for. A label with zero prefetching handles is itself a finding and
    should be reported as one, not dropped.

C4. "SEPARATION" WAS DECLARED HERE, ON DATA WHERE NOTHING SEPARATES.
      best |rho| = 1.000 (frac_large_gap) -> VERDICT: SEPARATION
    The arm it came from has 5 non-NaN handles: follow-through = (0.004514, 0, 0, 0, 0) and
    frac_large_gap = (0.000, 0.125, 0.125, 0.125, 0.125). Four ties on both axes; one
    handle differs. Perfectly monotone by construction => rho = -1.000 on one effective
    degree of freedom, picked as the max over 6 features x 4 labels with no out-of-sample
    gate and no minimum n. The "<- holds on both arms" annotation fires for streamA and
    streamB, which are the SAME workload replicated — it looks like cross-arm validation
    and is not.
    Asks: a minimum non-NaN handle count and a tie-mass guard before any verdict; make the
    verdict require the fitted relation to hold out-of-sample rather than advising it in
    prose; report the feature's rho on the TEST arm, not the max over arms.

C5. THE COLD-TAX COUNTER OVER-COUNTS A SEQUENTIAL READER (matters for MY prediction).
      arm      per-handle cold_small_reads / waste
      stream   24-65 reads, 22.0-56.9 MiB per handle (297 reads, 259.9 MiB over 12)
      scatter  17 reads, 16 711 680 B per handle     (204 reads, 191.2 MiB over 12)
    For the contiguous reader the chunks cold-fetched at whole granularity are CONSUMED by
    that same handle's following reads — net waste ~0, reported 259.9 MiB. `waste =
    chunk - read_len` never nets out later coverage. I did that netting by hand in gate 5f
    ("net of 16 later hits, ~15 MiB"); the tool should too, because otherwise met's
    streaming handles inflate the total and my pre-registered 1.0-1.4 GB prediction gets
    scored against a quantity I did not predict.
    Also: `state_before == cold` includes RE-entries into cold (seq->cold transitions are
    real, gate 5e saw them), not just the pre-decision phase. Both directions inflate.
    Ask: report cold_small_read_waste_NET_bytes (chunk bytes never subsequently read),
    and split first-cold-run from re-entries.

C6. Smaller: the config header makes the trace self-describing for the WINDOW decision but
    not for the GRANULARITY one — byteExactThreshold (= NICBytesPerSec x TTFB, clamped to
    [ExtentSize, ChunkSize]) is not in it, so the cold-tax number depends on the analyst
    passing -byte-exact-threshold correctly. Add byte_exact_threshold, chunk_size,
    extent_size (and nic_gbps) to the header.

C7. Interpretive, not a bug: per-handle follow-through is what we agreed to score, but the
    cache is GLOBAL. Under 48 ranks, bytes prefetched for handle A that handle B reads
    still save a fetch, so the per-handle metric is a LOWER bound on prefetch's value and
    could condemn a policy that pays off cross-handle. Both are computable from one trace.
    Ask for byte_follow_through_handle AND byte_follow_through_global as separate columns.

PROBE CAVEAT, STATED BECAUSE IT LIMITS PART C
---------------------------------------------
The 12 stream handles read overlapping spans of one object, so the kernel page cache
absorbed most reads: fh1 recorded 193 rows and the other eleven 24 each. Part C therefore
demonstrates the INSTRUMENT's behaviour on real traces; it is not evidence about GCHP's
handles. Every defect above is a property of the tool, reproducible from the artifacts.

WHAT THIS BUYS
--------------
The capture is still the deliverable, and it still costs a cluster job. Doing this first
means that job will not be spent producing a verdict that was void before the data landed:
C1 alone would have diluted every follow-through number by ~12x and C2/C3 can decide the
verdict by arm order.
