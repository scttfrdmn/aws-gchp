GATE 5f-I — #291 ON THE 58 ms ENDPOINT: BOTH MECHANISMS LOSE (lith#256)
2026-09-30, ~$0.55 of egress
================================================================================

WHY: upstream read the code and killed my mechanism outright — windowCap() is
floor(consumed * ratio / blockSize) and Observe() does `consumed += length` before
any gate, so the cap schedule is a pure function of the BYTE STREAM and is
identical at any RTT. Evidence accrues per byte, not per second; my "throughput
is RTT-bound so evidence accrues slower" has no step where time enters. They
proposed a better account (the floor is a constant 2 blocks = 16 MiB, which is 38
round trips of reading in-region and 1.4 cross-region, so below ~1.5x of margin
it is a race, and a race gives two modes), shipped the derived-floor fix as #291,
and said explicitly that they could not verify it collapses the high mode because
they have no 58 ms endpoint. They also asked for the one observable my 5f-H
archive was missing: --pf-trace with the window column on one slow and one fast
cell.

  They were right that my archive was deficient: gate-ramp-reader.sh never passed
  --pf-trace and ran --log-level warn, so all 36 mount logs were 0 bytes. Both are
  fixed (PF_TRACE=1, LOGLVL=info) and every cell below carries a trace.

SETUP  builds: lith-new = v1.1.3-15-gb3d78d8 (pre-fix), lith-291 = 5c6d8a0 (the
  merged #291), built from a clean worktree. Same us-west-2 copy of the same
  object, same us-east-1 head node, connect RTT 2.2 ms vs 58.6 ms. dd bs=1M,
  ratio {0,4}, n=8 per cell, fresh cold mount + unique port + --pf-trace per cell.
  All four cells of the 2x2 ran in ONE session, so no time-of-day confound.

RESULT 2 — THE TRACE SAYS WHY, AND IT'S THE OBSERVABLE THEY ASKED FOR
  The window series is BIT-IDENTICAL between a slow cell and a fast cell of the
  same arm:
    #291 r4, 20.34 s cell:  6432 nonzero windows, min 30, max 223,
                            first window>=223 at off 469.8 MB, dispatched 323
    #291 r4,  3.43 s cell:  6432 nonzero windows, min 30, max 223,
                            first window>=223 at off 469.8 MB, dispatched 323
  Identical. Same for the old build (min 4, max 223, first 223 at 469.8 MB,
  dispatched 323, in both a 13.38 s and a 4.16 s cell).

  So the window trajectory CANNOT be what distinguishes a slow cell from a fast
  one — it is a pure function of the byte stream, exactly as upstream's code
  reading says. Whatever the two modes are, the ramp is not the discriminator.
  This is the single most useful thing the trace produced and neither of us had it.

RESULT 3 — #291 DID CHANGE THE FLOOR, AND IT STILL DIDN'T MATTER
  old  build: min nonzero window 4 blocks; 448 of 6432 windows below 30
  #291 build: min nonzero window 30 blocks; ZERO windows below 30
  The fix works as designed — it lifted every sub-30 window off the floor — and
  the high-mode rate did not move. That is the cleanest possible statement that
  the floor was not the binding constraint.

  Ratio 0 is the natural "infinite floor" control: window is 223 from off 8.4 MB
  onward, and it still produced a 38.96 s cell. A full 223-block window does not
  immunise the read. So the gate raises the PROBABILITY of a stall (pooled over
  both sessions today: >9 s in 1 of 32 ratio-0 cells vs 16 of 32 ratio-4 cells)
  without the window being the mechanism within an arm.

RESULT 4 — WHY #291 COULD NOT HAVE HELPED, AND IT'S A BUG WORTH FIXING ANYWAY
  RoundTripBytes() = nicBPS * currentTTFB(), read ONCE at Open() (fs.go:605).
  currentTTFB() returns ttfbSeed when there are no samples (fill.go:70-71), and
  cmd_mount.go:326 sets ttfbSeed = 40 ms unconditionally.
  A single-handle reader on a fresh mount opens BEFORE any fill has recorded a
  TTFB, so it always gets the seed:
      50 Gbps -> 6.25 GB/s * 0.040 s = 250 MB -> ceil / 8 MiB = 30 blocks
  MEASURED, and this is the proof: min nonzero window is exactly 30 blocks at
  BOTH endpoints — in-region (probe291) and cross-region (xr291). The true
  58.6 ms round trip wants 366 MB = 44 blocks. So the derived floor NEVER ADAPTS
  for the reader it was written for; it is a constant 30 blocks at 2.2 ms and at
  58.6 ms alike. Whether it helps is untestable in this regime until the floor is
  refreshed after the first fill (or seeded from the endpoint).

RESULT 5 — THE INERTNESS CLAIM DOES NOT HOLD IN-REGION ON A COLD MOUNT ($0)
  Same 40 ms seed, opposite sign. #291 asserts the derived floor equals the old
  constant at 2.2 ms — true once TTFB samples exist, false at first Open. Re-ran
  all six in-region gate-5f-E arms at ratio 4 on both builds:
    arm        old s3 MB   #291 s3 MB   distinct MB   verdict
    met/whole     1217.8      1217.8       1217.9     unchanged
    met/var1        59.8       210.8         22.5     3.53x MORE BYTES
    met/sub         22.8        22.8         11.3     unchanged
    hco/whole      852.0       852.0        851.4     unchanged
    hco/var1       371.8       371.9         86.1     unchanged
    hco/sub         52.6        52.6          6.3     unchanged
  met/var1 is the arm the flag's headline saving came from: 95.09% of bytes saved
  vs ratio 0 becomes 82.69%. 151 MB of the 1158 MB saving handed back — 13% of the
  win — on the arm that wants only 22.5 MB of distinct data while the floor alone
  commits 240 MiB. hco/var1 is untouched because its own earned window already
  exceeded 30 blocks.
  So "provably inert in-region" holds for a warm mount and not for a cold one,
  and cold single-open is the regime ordinary tools run in.

WHAT I'D CONCLUDE
  1. My accrual mechanism is dead (their code reading, not my measurement).
  2. Their floor mechanism is not supported either: the fix lifted every sub-30
     window and moved the high-mode rate not at all, and slow/fast cells have
     identical window traces.
  3. The stall is somewhere that the window does not parameterise — dispatch
     scheduling, connection pool, or the endpoint itself. Ratio 4 still triples
     the stall rate (1/32 vs 16/32), so the gate is implicated; the window is not
     the channel.
  4. #291 should still land, but with the seed problem fixed, because as written
     it is a constant 30-block floor everywhere and it costs 13% of the flag's
     byte win on a cold low-coverage read.
